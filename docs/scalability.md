# 확장성 설계 노트 — 비동기·부하분산을 "구현하지 않은" 이유와, 대신 한 것

> 요약: 온라인 쇼핑몰이니 비동기 처리와 부하분산이 필요하지 않을까? — 이 질문에 **측정으로 답했다.**
> 결론은 셋이다. ① 실시간 주문은 과제가 **동기(SYNC) 계약**을 명시했으므로 구조를 바꾸지 않는다.
> ② 그 대신 몰릴 때 **약속을 지키기 위한 최소 장치(과부하 차단)** 를 넣었다.
> ③ 측정해 보니 진짜 한계는 서버 대수가 아니라 **외부 FTP 접속 대기**와 **초 단위 파일명 규칙**이었다 — 둘 다 서버를 늘려서는 풀리지 않는다.

---

## 1. 질문의 출발

토토는 주문량이 급격히 늘어 연계를 의뢰한 쇼핑몰이다. 그렇다면 주문 API를 비동기(접수만 하고 나중에 처리)로 바꾸거나,
서버를 여러 대 두어 부하를 나눠야 하지 않을까?

바로 구현하기 전에 두 가지를 먼저 확인했다. **계약이 무엇을 요구하는가**, 그리고 **실제 병목이 어디인가.**

## 2. 먼저 계약을 확인했다 — 비동기 전환은 요구사항 위반

과제는 시나리오 1을 이렇게 정의한다.

- "SYNC 전송 성공/실패 유무를 반환 받음(응답: JSON)"
- "(2), (2.2)가 모두 처리 되었을 때 주문자에게 처리 결과를 반환"

"일단 접수(202 Accepted)하고 나중에 처리" 방식은 이 계약을 정면으로 어긴다.
EAI에서 동기·비동기는 성능 튜닝 옵션이 아니라 **인터페이스 계약**이다. SAP PO/IS에서도 같은 흐름을
Sync(요청-응답)로 둘지 Async(EO/EOIO, 큐 기반)로 둘지는 송·수신 시스템과 합의해서 정한다.
그래서 **"실시간 주문의 동기 구조는 바꾸지 않는다"** 를 먼저 결정했다.
(시나리오 2 — 주문 → 운송 — 는 이미 5분 배치로 두 시스템을 비동기로 분리한 구조다.)

## 3. 그래도 질문은 유효하다 — 병목을 숫자로 봤다

실서버에서 잰 단계별 시간(모니터링 로그의 `steps`)은 다음과 같았다.

| 단계 | 실측 | 비고 |
|---|---|---|
| DB 접속 | 0.3 ~ 0.9초 | 요청마다 새 연결 |
| **FTP 접속·로그인** | **약 2.4초** | 요청마다 새 연결, 주로 서버 측 응답 대기 |
| 파싱·매핑·INSERT·업로드 | 합계 0.1초 안팎 | 63행 기준 |
| 커밋 | 0.3 ~ 0.5초 | |

주문 1건은 대부분의 시간을 **외부 시스템을 기다리는 데** 쓴다. 동시에 8건을 처리한다면 이론상 처리량은 약
`8건 ÷ 2.8초 ≈ 2.9건/초`. 그렇다면 그 이상 몰리면 무슨 일이 생기는가?

## 4. 왜 "로컬에서" 측정했나

회사 서버로 부하 테스트를 하는 것은 **금지 사항으로 판단했다.**
점검 결과 수신 FTP는 업로드 전용(삭제·이름변경 불가), DB 계정은 DELETE 불가다.
초당 10건 부하를 15초만 줘도 **지울 수 없는 영수증 파일 150개와 주문 수천 행**이 다른 지원자와 함께 쓰는 서버에 남는다.

그래서 이렇게 측정했다 (`./gradlew loadTest`, 코드: [LoadTest.java](../src/test/java/com/inspien/eai/load/LoadTest.java)).

- **애플리케이션 코드는 그대로** — 실제 `RestSender`·`OrderSyncFlow`를 띄운다
- 외부 시스템만 H2(Oracle 모드)와 가짜 FTP로 바꾸고, **실서버에서 잰 지연을 주입**한다 (DB 접속 300ms, FTP 접속 2,400ms, 업로드 40ms)
- 부하는 **open-loop(초당 고정 도착률)** — 실제 주문자는 서버가 느려졌다고 덜 보내지 않는다
- 클라이언트 타임아웃 30초, 측정이 끝난 뒤에도 서버가 대기열을 다 비울 때까지 기다렸다가 DB를 센다

## 5. 측정 결과

측정 환경: macOS / Java 25 / 14코어, 요청당 10행 ([원본](load-test-result.md))

| 시나리오 | 요청 | 성공 | 거절(503) | 클라이언트 타임아웃 | 처리량 | 성공 응답 p50 / p95 | 거절 응답 p95 | **적재됐지만 응답 못 받음** | 영수증 파일명 앞당김 |
|---|---|---|---|---|---|---|---|---|---|
| A. 평시 2건/초 (차단 적용) | 30 | 30 | 0 | 0 | 1.7/초 | 2.8초 / 2.8초 | - | 0 | **14초** |
| B. 몰림 10건/초 (**차단 없음 — 도입 전**) | 150 | 112 | 0 | **38** | 2.5/초 | 14.5초 / 28.2초 | - | **38건** | 74초 |
| C. 몰림 10건/초 (**과부하 차단**) | 150 | 48 | 102 | 0 | 2.7/초 | 2.8초 / 2.8초 | **7ms** | **0** | 31초 |
| D. 외부 지연 0 · 50건/초 (차단 적용) | 500 | 500 | 0 | 0 | 50/초 | 2ms / 5ms | - | 0 | **488초** |

### 5.1 B — 차단이 없으면 "느려짐"이 "정합성 문제"로 번진다

과부하 차단 이전 구조(처리 스레드 8개 + 무제한 대기열)에서는 넘치는 요청이 전부 대기열에 쌓인다.
대기 시간이 처리 시간을 넘어서면서 응답이 14초, 28초로 늘었고, **38건은 30초를 넘겨 주문자 쪽에서 타임아웃**이 났다.

문제는 그 38건이 **서버에서는 끝까지 처리됐다는 것**이다. DB에 적재되고 영수증 파일도 나갔는데, 주문자는 "실패"로 알고 있다.
주문자가 재전송하면 같은 주문이 두 번 적재되고 영수증이 두 번 나간다. 그리고 FTP 파일은 지울 수 없다.
**몰림이 단순히 "느림"이 아니라 되돌릴 수 없는 중복 데이터로 이어진다.** 이 결과 때문에 과부하 차단을 구현하기로 했다.

### 5.2 C — 과부하 차단: 처리량은 그대로, 약속은 지킨다

동시 처리 수에 상한(8건)을 두고, 넘치는 요청은 **처리를 시작하기 전에** 즉시 `503 OVERLOADED`(`retryable: true`, `Retry-After: 1`)로 돌려준다.

- 받은 요청: 평시와 같은 2.8초에 응답
- 못 받은 요청: **7ms** 만에 거절 — 아무것도 쓰지 않았으므로 재전송해도 안전
- 응답을 잃은 주문: **0건**

처리량은 2.5 → 2.7건/초로 사실상 같다. **과부하 차단은 처리량을 늘리는 장치가 아니다.**
받은 요청은 제시간에 끝내고, 못 받는 요청은 빨리 알려서 "처리됐는지 모르는 상태"를 없애는 장치다.
운영자는 `GET /health`의 `ordersInFlight`·`ordersRejected`로 지금 한계에 걸려 있는지 바로 본다.

### 5.3 A·D — 진짜 한계는 서버가 아니라 계약에 있었다

영수증 파일명 규칙은 `INSPIEN_참여자명_yyyyMMddHHmmss.txt`, **초 단위**다. 같은 초에 두 파일을 만들 수 없으므로
구현은 다음 초 이름을 배정해 충돌을 피한다. 측정해 보니 이것이 생각보다 훨씬 빨리 한계가 된다.

- **A. 평시 2건/초**만 돼도 15초 동안 파일명이 실제 시각보다 **14초 앞당겨졌다.** 초당 1건을 넘는 순간 밀리기 시작한다
- **D. 외부 지연이 0**이면 서버 한 대가 50건/초를 2~9ms에 처리하는데, 파일명은 **488초(8분) 앞당겨졌다**

D는 두 가지를 보여준다.
1. **서버 처리 능력은 병목이 아니다.** 외부 대기가 없으면 한 대로 50건/초를 넘게 처리한다. 지금 병목은 FTP 접속 대기다
2. FTP를 아무리 빠르게 해도 **"주문 1건 = 파일 1개, 초 단위 파일명"이라는 계약으로는 초당 1건을 넘는 순간 파일명이 실제 시각을 나타내지 못한다** — 회계 담당자가 파일명 시각으로 정산하거나 정렬한다면 그대로 오류가 된다

## 6. 그래서 비동기와 부하분산을 구현하지 않았다

| 선택지 | 구현하지 않은 이유 |
|---|---|
| 실시간 주문 비동기화 | 과제가 SYNC 응답을 계약으로 명시했다. 바꾸는 것은 기술 선택이 아니라 **계약 변경**이고, 송신측(토토)과 협의할 사항이다 |
| 영수증 집계 전송 (1분 단위 묶음) | 5.3의 한계를 푸는 진짜 해법이지만, 파일 형식·전송 주기를 바꾸는 일이라 **수신측(회계)과 협의**해야 한다 |
| 서버 여러 대 (부하분산) | ① 측정상 병목은 서버가 아니라 FTP 접속 대기다(D). 서버를 늘려도 대기는 그대로이고, 오히려 FTP 서버의 동시 접속 부담만 커진다 — **병목이 아닌 곳을 넓히는 일**이다. ② 지금 구조에서는 여러 대가 바로 충돌한다. 주문번호 채번이 프로세스 메모리 기준이고, 초 단위 파일명이 서버끼리 겹친다. 둘 다 DB 기반 채번과 파일명 규칙 협의가 먼저다 |

반대로 배치(시나리오 2)는 이미 여러 대에 안전하다. 처리권을 `UPDATE … SET STATUS='Y' WHERE … AND STATUS='N'`로
선점하므로, 두 인스턴스가 동시에 돌아도 한 쪽만 처리한다.

## 7. 대신 구현한 것

| 장치 | 근거 |
|---|---|
| **과부하 차단** — 동시 처리 상한(`ORDER_MAX_CONCURRENT`, 기본 8), 초과 시 처리 전 즉시 503 | B의 "응답 못 받은 38건" → C에서 0건 |
| HTTP 처리 스레드와 대기열에 상한 (32스레드 / 200건, 넘치면 수신 스레드가 직접 처리해 역압) | 무제한 대기열은 메모리와 응답 시간을 함께 무한정 키운다 |
| `GET /health`에 `ordersInFlight` · `maxConcurrentOrders` · `ordersRejected` | 운영자가 한계 도달 여부를 바로 확인 |
| 로컬 부하 측정 도구 (`./gradlew loadTest`) | 설정을 바꿀 때마다 같은 조건으로 다시 잴 수 있다 |

## 8. 운영이라면 — 단계별 로드맵

> 피크 1,000건/초를 가정한 상세 운영 설계(Outbox·Kafka·집계 영수증·클러스터링·장애 시나리오)는 [production-design.md](production-design.md)에 있다.

| 단계 | 내용 | 기대 효과 | 계약 변경 |
|---|---|---|---|
| **1. 계약 유지** | FTP 세션 풀(접속 2.4초 제거), DB 커넥션 풀 | 주문당 약 0.4~0.6초(남는 것: 커밋·업로드) → 동시 8건 기준 이론상 약 15~20건/초 (단, 파일명 한계는 그대로) | 없음 |
| | `Idempotency-Key` 헤더 + 처리 이력 | B 같은 상황에서 재전송해도 중복 적재 없음 (근본 해결) | 송신측에 헤더 추가 요청 |
| **2. 계약 변경 협의** | 주문은 DB 커밋까지 SYNC, 영수증은 큐(Kafka, SAP IS JMS 등)에 넣고 1분 단위로 모아 전송 | 파일명 초 단위 한계 해소, FTP 장애가 주문 접수를 막지 않음 | 회계와 파일 규칙·주기 협의 |
| **3. 수평 확장** | 채번을 DB 시퀀스·채번 테이블로, 파일명에 인스턴스 구분 | 서버 여러 대 운영 | 파일명 규칙 협의 |

## 9. 한 줄로

**"쇼핑몰이니까 비동기·부하분산"이 아니라, 계약을 먼저 확인하고 병목을 측정했다.**
그 결과 서버를 늘리는 대신 **몰릴 때도 약속을 지키는 장치(과부하 차단)** 를 넣었다.
남은 한계(FTP 접속, 초 단위 파일명)는 코드가 아니라 **계약 협의로 풀어야 하는 문제**라는 근거를 숫자로 남겼다.
